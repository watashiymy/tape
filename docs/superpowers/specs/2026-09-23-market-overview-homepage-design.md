# 「市场概览」首页（2026-09-23）

## 0. 起因与用户决定

用户原话：「给系统增加一个首页，其中内容包含 A 股指数行情、市场情绪等数据，用户可以对市场的总体情况有个直观的了解——如果没有免费的数据源，那就算了。」

先实测数据源（§1），再逐条问定：

| 问题 | 用户选择 |
|---|---|
| 什么时候看 | 盘中、收盘后**都看** |
| 落地页 | **首页当落地页**，任务控制台退到第二（推翻 2026-09-05「控制台当落地页」的决定） |
| 盘中怎么更新 | **自动刷新**，收盘后停 |
| 放哪些板块 | 指数行情 / 涨跌家数与分布 / 涨停·跌停·炸板·连板 / 趋势宽度（收盘后），四项全要 |
| 收盘数据怎么更新 | **首页上点一下**（不并进信号跟踪，也不在打开页面时自动跑） |
| 盘中数据谁去取 | **方案 A**：页面自己取 + 短缓存 + 定时局部刷新（否决方案 B：常驻采集进程） |
| 数据会不会越来越多 | 快照按滚动窗口保留，占用有上限（§5.5） |
| 恐慌指数 | 调研后用户决定**先不要**（结论见 §9，留档备查） |

本设计经过三轮评审：第一轮 4 个视角加逐条对抗式复核，76 条意见中 71 条成立；第二轮核对解决情况并找新问题，补了 32 条；第三轮专查前两轮的改动有没有互相矛盾，又抓出 11 条（其中 3 条会让状态机自相矛盾）。都已并入正文。

**时钟假定**：沿用全项目的约定，本机时钟即北京时间（与控制台、信号页的 `date.today()` 一致）。

## 1. 免费数据源实测结论（2026-09-23 盘中到 19:45，均经独立复核）

**盘中实时（非官方网页接口，免费、无授权说明、可能改版）**

- **腾讯 `qt.gtimg.cn`**（GBK）
  - 一次请求可批量拿全部指数，也可以顺带拼上 `bkqtRank_A_sh,bkqtRank_A_sz`；约 3 秒一个快照。
  - 字段按 `~` 的位置解析，已用算术和新浪逐项交叉验证。
  - `web.ifzq.gtimg.cn/appstock/app/minute/query` 给当日分时、交易日期 `data.date`，以及交易状态串 `qt.market`：它是一个只含一个字符串的 list，用 `|` 分隔，例如 `SH_open_交易中`，里面没有 BJ。
  - `proxy.finance.qq.com/.../newfqkline` 给含成交额的日 K，单位万元，**盘中带着当天未走完的 bar**。
- **新浪 `hq.sinajs.cn`**（GB18030）
  - 必须带 `*.sina.com.cn` 的 Referer，否则 5 秒后返回 403。
  - 同一秒与腾讯数值一致。它没有涨跌额、涨跌幅字段，但有 `[30]` 日期、`[31]` 时间、`[32]` 状态码。
- **东方财富 `push2ex`**（涨跌分布 `getTopicZDFenBu`、涨停池 `getTopicZTPool`、炸板池 `getTopicZBPool`）
  - 两次调研合计 40 多次请求，0 失败。`ut` 是网页内置的固定值。
  - 池子**必须带 `date`**。返回的 `qdate` 永远是服务器当天，**不能**当数据日期用。
  - 日期不对或超出约 15 个交易日的保留期时，返回 `rc=0, tc=0` 的空池，**不报错**。
  - 分布接口不理 `date` 参数，自身也不带数据日期。**收盘后至少 20 分钟里它还在变**（15:16–15:19 跌停档为 12，15:20 起变为 13）。
- **东方财富 `push2` / `push2his` 的批量行情、日 K、板块排行**：**要浏览器 cookie 才放行**，复核用 A/B 测试证实，不是限流。这些接口不用，也不模拟 cookie、不绕反爬。

**收盘后（官方口径，项目已在用的 baostock）**

- `query_daily_history_k_AStock(date)` 是 **0.9.3 才有**的接口。一次请求（13~27 秒）拿到全沪深约 5220 只当日日线，含除权昨收、ST 标记、停牌标记，不含北交所。
  - 当天数据：文档写 17:30 入库；实测 15:44 仍为空，19:16 已有，17:30 这个时点本身没亲眼验证过。
  - 所有字段都是字符串。停牌行的 `pctChg/turn/volume/amount` 是空串。
  - **error_code 非 0 = 取数失败**，其中**会话类错误码**（实测中途失效过一次，`10001001 用户未登录`）要重新登录，其他非 0 错误码不登录（§5.2）。如果只按 `while rs.error_code=="0" and rs.next()` 读、不回头查错误码，失败会变成一张静默的空表。**真正的空结果**：error_code 为 0 且 0 行。两者必须先判错误码、再判行数。
- 用 `close/preclose` 逐日连乘推出的复权价，与 baostock 复权因子的误差 < 1e-6。
- `query_trade_dates` 能返回**未来**日期，已实测到 2026-12-31，包括 9 月 25 日中秋、10 月 1~7 日休市。

**已核实的口径（写进图注）**

- 东财涨跌分布 = **沪深京 A 股，不含 ST 与停牌股**：用 baostock 加新浪北交所自己分档，23 档逐档对上。
  - 0 = 涨跌幅恰为 0；±1…±9 = 按未四舍五入的涨跌幅向上取整（如 0~1% 含 1%）；±10 = 超过 9% 但未封板（含 20%/30% 板与新股）；±11 = 封住涨停/跌停。
  - 「±11 只算有封单的」目前只有 1 天、1 个反例的证据，**待复核**（§10）。
- 腾讯 `bkqtRank_A_sh/sz` = 沪深 A 股，**含 ST，停牌计入平盘**，不含北交所。与东财分布不是一个口径，**不放在一起比**。
- 腾讯/新浪行情里深证成指的成交额 = 深市全部（与深证综指逐位相同）；创业板指 = 创业板全板；沪深300 = 成分股。**各指数的「成交额」含义不一**。
- 主板 ST 的涨跌幅限制现为 **10%**（实测 *ST 美芝 −10.01%），不是 5%。

## 2. 页面

侧栏第一项「市场概览」（`url_path="home"`，`default=True`，挂在根路径 `/`）。从上到下按「快 → 慢」排列：

1. **状态条**：状态 + 数据源自带的时刻或日期（§4）。
2. **指数行情**：6 张卡片，每张显示点位、涨跌额、涨跌幅和当日分时小图（虚线为昨收），红涨绿跌。
   - 代码（腾讯与新浪相同）：`sh000001` 上证指数、`sz399001` 深证成指、`sz399006` 创业板指、`sh000688` 科创50、`sh000300` 沪深300（**不是** `sz399300`）、`sh000852` 中证1000。
   - **与示意图不同**：卡片**不显示各自的成交额**。各指数成交额口径不一（§1），挂在卡片上会让人以为可以横比；成交额只在下一行按两市合计显示。
3. **两市成交额**：上证 + 深证成指，即沪深两市全部，含极少量 B 股。写法按一条明确的判据区分：
   - **`data.date` = 今天且现在早于 15:00**（含集合竞价和午间休市）：「X 万亿（截至 HH:MM）· 9 月 22 日全天 Y 万亿」，**不给百分比**。半天去比全天，数字必然难看且误导。
   - **其余情况**：「9 月 23 日全天 X 万亿 · 9 月 22 日全天 Y 万亿」。两个都是全天。**只有 §3 的口径一致性检查已做且通过时才追加「±Z%」**；没做过、没通过、或用新浪兜底，都只显示两个数。这一条是唯一判据，不再按时刻另行规定。
4. **涨跌分布**（左）：涨/平/跌家数 + 横向比例条 + 23 档柱状图（跌停 … 涨停）。
   - 家数由分档加总得出，所以和柱状图一定对得上。
   - 图注写统计范围与分档规则。±11 档的说法按时段区分：盘中写「封住涨停/跌停」，收盘后写「收盘封住」。
5. **涨停温度计**（右）：
   - 涨停、跌停：取分布的 ±11 档，与左图同源同轮；
   - 炸板率 = 炸板池家数 /（涨停池家数 + 炸板池家数）：两个池子用同一个 `date`、同一轮请求，**不跨接口拼分子分母**；
   - 最高连板：涨停池 `lbc` 的最大值。
   - 范围注「沪深京 A 股，不含 ST」（炸板池的范围按 §10 核实后再定稿）。
   - 分母为 0 时炸板率显示「—」；池子为空时最高连板显示「—」，不显示 0。
6. **趋势宽度（收盘后）**：4 张小卡片——站上 20 / 60 / 200 日线的占比，以及 52 周新高/新低家数。
   - 每张卡片附「分子/分母」只数，外加一幅近 60 个交易日的小图：均线占比用单条灰线；新高/新低画成上红下绿的柱，这里红绿本来就是涨跌语义。
   - 标题旁写「收盘数据截至 YYYY-MM-DD · 沪深 A 股，不含 ST 与当日停牌；每项只统计交易天数足够的股票」。
   - 下方是按钮区（§5.4）。
7. 页脚一行小字：盘中数据来自门户网站公开行情，可能有几秒延迟。

**小图的做法**
- Streamlit 1.61 的 `st.html` 用 DOMPurify 过滤，而且只开了 html 配置，**内联 `<svg>` 会被整段删掉，页面也不报错**。评审读前端源码时证实了这一点。
- 所以小图做成 `<img src="data:image/svg+xml;base64,…">`，和 `theme.BRAND_LOGO` 同一种做法，`img` 在过滤白名单里。
- 生成 SVG 的纯函数放在 `src/quant/report/`。色值用 palette 常量写死，因为 `img` 里的 SVG 拿不到页面的 CSS 变量和网络字体；刻度、档位名这类文字放在 SVG 外面，用 HTML 排。
- 不用 plotly：每 30 秒要重画 6 幅分时图和 1 幅分布图，而且这些图都不需要交互。

**术语就地解释**：炸板、炸板率、连板、站上 N 日线、52 周新高/新低、分布的档位，每个术语一句话，挂在卡片的 `?` 上，只讲它量的是什么、数值偏高或偏低说明什么，不写操作建议。文案常量放在 `guide.py`，用 `HOME_` 前缀。

**分层**：`src/` 与脚本不能 import `app/`（progress.py 与 charts.py 的既有约定）。所以：
- `session.py` 只返回**状态枚举**，文案映射放在 `guide.HOME_`；
- 收盘数据的就绪时刻只在 `quant.market` 定义一处（`BREADTH_READY`），`guide.FACTS["breadth_ready"]` 引用它，任务脚本也直接用它。
- **不复用** `FACTS["data_ready"]`：那个值说的是信号跟踪和扫描所用日 K 的就绪时刻，由另一个接口决定。等 §10 实测后两者可能不同。

**配色**：状态条和按钮区只用 running/idle 两种 pill（琥珀/灰），**不用** success/failed 的绿/红，免得和满屏的红涨绿跌读反。「数据延迟」和「任务失败」靠文字表达。

**首次使用引导**（从没跑过任何任务时，给一条去「使用说明」的链接）从控制台挪到首页，因为引导应该出现在落地的那一页。

## 3. 数据来源、兜底与校验

**原则**

- **一个数字只认一个来源**，不跨来源拼凑。兜底是整块替换，范围标签跟着换。
- 每个来源取回后先过**按来源分别写的**校验；**校验不过就当这次没取到**，绝不显示可疑的数。
- 采用顺序：**主源本轮 > 兜底源本轮 > 最近成功值 > 「暂不可用」**。
- 最近成功值存成（数值, 来源, 范围标签, 数据源时刻, 交易日）。
  - 它的交易日 ≠ 当前交易日时，时刻一律带日期显示（「9 月 23 日 15:20」）。
  - **交易时段里不显示跨交易日的旧值**，直接显示「暂不可用」。
  - 这份状态放在一个可以 reset 的对象里，测试时要清空。

| 板块 | 主来源 | 兜底 | 校验（任一不过 = 本次失败） |
|---|---|---|---|
| 指数点位/涨跌 | 腾讯 `q=<6 个代码>,bkqtRank_A_sh,bkqtRank_A_sz`（1 次） | 新浪 `list=<6 个代码>`（1 次，**同一轮并发发出**，主源失败才采用） | **腾讯**：每个期望的 `v_<code>` 都在（批量请求里写错的代码整段不出现，单个请求时返回 `v_pv_none_match`），且段数 ≥ 所用最大下标 + 1（各代码段数本就不同，sh000001 是 88 段，bj899050 是 87 段，不能比相等）；`|[31] − ([3] − [4])| ≤ 0.011`；`|[32] − 100×[31]/[4]| ≤ 0.006`；价格 > 0；最高 ≥ max(开, 现)、最低 ≤ min(开, 现)（集合竞价期是否适用，等 §10 实测后再定）。**新浪**：段非空；`[30]` = 预期交易日（定义见下）；`[32] == "00"`；名称对上；价格 > 0；高低关系成立；涨跌额与涨跌幅由我们自己算 |
| 分时小图 + 交易日期 + 交易状态 | 腾讯 `minute/query`（每只 1 次，共 6 次） | 交易日期：6 次里成功的那些必须一致；全部失败则按 §4 的判定链处理。小图：缺了不画，数字照常显示 | 时间单调、价格 > 0、`data.date` 可解析 |
| 两市成交额（当前） | 与指数行情同源（腾讯 `[37]` 万元 / 新浪 `[9]` 元） | 随指数行情整块切换 | 两项都有值且 > 0 |
| 两市成交额（上一交易日全天） | 腾讯 `newfqkline`，上证、深成指各 1 次；缓存键 = **（当前交易日 `data.date`, 当天那根是否已定格）**。「已定格」= 非交易日或 `data.date` 早于今天（那根本来就走完了），或今天已过收盘截止时刻（§4.2）。这个量单调不回退，所以昨晚做过的检查今早不会被丢掉 | 无（缺了只显示当前值） | 取**日期严格早于 `data.date`** 的最后一根。**口径一致性**：每次取到「已定格」的 K 线时做一次——K 线里 `data.date` 当天那根的成交额与行情快照 `[37]` 相差 < 1 万元。`[37]` 是截断后的整数，走完的 bar 带两位小数，所以不能比相等。结论随 K 线一起缓存。没定格就不做检查，这时也不给百分比。用新浪兜底时不做检查、不给百分比 |
| 涨跌家数 + 分布 | 东财 `getTopicZDFenBu`（1 次） | 腾讯 `bkqtRank`（已拼在行情请求里）：只有家数，分布图显示「暂不可用」，范围标签换成「沪深 A 股，含 ST，停牌计入平盘」 | **东财**：23 档齐全、非负整数、合计在 [4000, 7000]。**腾讯**：沪、深两段都在；涨 + 平 + 跌 = 总；合计在 [4000, 7000] |
| 涨停温度计（一整块） | 涨停/跌停取分布 ±11；炸板率、最高连板取东财涨停池 + 炸板池（2 次，`pagesize` 给足，按 §10 实测上限，不够就翻页） | 无。分布或池子本轮失败，整块沿用上一次**同一轮**成功的快照并标出它的时刻，不跨轮拼 | 池子的 `date` **只取预期交易日**（定义见下），**禁止用 `qdate`**；还不知道交易日就不请求池子。返回家数 = 明细条数；`lbc` 为正整数。**日期对账**：涨停池 `tc = 0` 而分布 +11 档 > 0，或两者相差超过 5，就判「分布与池子不属于同一交易日」。两个接口不是同一瞬间取的，所以不要求严格相等 |

**预期交易日**：新浪的日期校验、池子的 `date` 都用它。按顺序取第一个有的：
1. 本轮腾讯分时的 `data.date`（6 次里成功的那些必须一致）；
2. 本地交易日历推出的「最近一个已开盘的交易日」：今天是交易日且已过 9:15 就是今天，否则是上一个交易日；
3. 上一轮成功的 `data.date`。

三者都没有时，新浪只要其余校验通过，就允许用它自己的 `[30]` 作日期，但状态条按 §4.1 显示「状态未知」，也不请求池子。

**分布的日期**：分布接口自己不带日期，所以它的日期 = 池子的 `date`，**前提是日期对账通过**。三种情况下分布和温度计本轮都按失败处理，回落到最近成功值或「暂不可用」：
- 对账不通过（例如 9:20 分布还停在昨天、池子已经是今天）；
- 拿不到预期交易日，因而没请求池子；
- 池子本身请求失败。

**绝不**拿行情来源的日期给分布贴标签——那正是「把昨天的分布标成今天」的入口。

**一轮怎么发**

- 分两段：
  - 第 1 段并发发出：腾讯行情（含 bkqtRank）、新浪行情、6 次分时、东财分布；
  - 第 2 段发 2 个池子，用第 1 段拿到的交易日。
- 每轮 11 个请求。实测单个请求 50~400 ms，每轮总计约 0.5 秒。`newfqkline` 每个交易日只取一次（2 个请求）。
- 单个请求连接超时 2 秒、读取超时 3 秒，整轮最迟 6 秒收口，超时的来源当作失败处理。
- 一轮结果用 `st.cache_data` 缓存，多个浏览器标签页共用。有**两个缓存入口**，按 §4.2 那一行的定时选：定时 ≤ 60 秒且要取数的时段（集合竞价到收盘截止时刻）用 `ttl=25`；其余「每次整页加载取一次」的时段（非交易日、盘前、午休、收盘截止时刻以后）用 `ttl=600`。**不写死 15:30 这类字面量**，切换点跟着 §4.2 的收盘截止时刻走。两个入口都必须写 `show_spinner=False`：它默认会把函数名显示出来，违反文案规则。

**不做的事**：不模拟 cookie、不执行网页 JS。只带新浪要求的 Referer，那就是它自己的站点，它的网页本来就会带。

## 4. 刷新与时效

### 4.1 今天是不是交易日（判定链）

结果只有三种：**交易日 / 非交易日 / 未知**。按顺序判定，命中即停：

1. **周六、周日一律是非交易日**。A 股调休上班的周末也不开市。
2. 本地交易日历（§5.5 的 `calendar.parquet`）**覆盖今天**时，以它为准。
3. 数据源**请求成功**时：
   - `data.date` = 今天 → **交易日**。分时接口在休市日返回的是最近交易日，所以这条是安全的。**只认分时的 `data.date`**，不认会随请求时刻往前走的行情时间戳。
   - `data.date` 早于今天，且**已过判休市截止时刻** → **非交易日**。截止时刻暂定 9:45，按 §10 实测「分时 `data.date` 几点切到当天」再定。
4. 其余情况都是「**未知**」，包括请求失败、以及截止时刻之前 `data.date` 还是旧的。**请求失败永远不计入判定。**

判定每轮都重做，没有终态。所以两种误判都能自愈：截止时刻前是「未知」，到 9:46 判成非交易日之后每 10 分钟仍取一次数，某一轮拿到今天的日期就按第 3 条回到「交易日」。

**冲突与失败时的显示**

- 日历说今天是交易日，但请求失败，或者过了截止时刻 `data.date` 仍早于今天：永远不判休市。状态条显示「数据延迟」，各板块显示数据自己的日期，绝不把昨天的数标成今天的。
- 结果为「未知」时，状态条显示「状态未知」，各板块显示数据自己的日期。**不报出「交易中 / 集合竞价 / 待开盘」**，那是没有依据的正面状态。取数节奏按 §4.2 的时钟行走，拿到可靠日期后立即重判。

### 4.2 状态表

**状态枚举**共 8 个：`休市`、`盘前`、`集合竞价`、`待开盘`、`交易中`、`午间休市`、`已收盘`、`状态未知`。外加一个**叠加标记** `数据延迟`（§4.3），它不替换状态，只在状态条上追加，也不改变取数与间隔。

判定顺序：非交易日 → `休市`（优先于所有时钟行）；未知 → `状态未知`；交易日 → 查下表。三种情况的取数与间隔都按下表所在时段那一行。

| 时段 | 状态（交易日） | 显示哪天的数据 | 取数 | 定时 |
|---|---|---|---|---|
| 非交易日（全天） | 休市 · 最近交易日 YYYY-MM-DD | 最近交易日 | 每次整页加载取一次；此后每 10 分钟一次 | 60 秒只看时钟 |
| 0:00–9:14 | 盘前 · 上一交易日 YYYY-MM-DD | 上一交易日 | 每次整页加载取一次 | 60 秒只看时钟，9:14 起切到取数 |
| 9:14–9:25 | 集合竞价 · 时刻 | 今天 | 每 30 秒 | 30 秒 |
| 9:25–9:30 | 待开盘 · 时刻 | 今天 | 每 30 秒 | 30 秒 |
| 9:30–11:30、13:00–15:00 | 交易中 · 时刻 | 今天 | 每 30 秒 | 30 秒 |
| 11:30–13:00 | 午间休市 · 11:30 | 今天 | 进入午休后补取一次（拿上午的终值）；此后每次整页加载取一次 | 60 秒只看时钟，13:00 起切回取数 |
| 15:00 至收盘截止时刻（暂定 15:30，以 §10 实测为准） | 已收盘 · YYYY-MM-DD | 今天 | 每 60 秒 | 60 秒 |
| 收盘截止时刻以后 | 已收盘 · YYYY-MM-DD | 今天 | 每次整页加载取一次（走长缓存） | 60 秒只看时钟 |

- **每个状态都挂定时**，只是间隔不同、联不联网不同。这样昨晚开着没关的标签页，今天 9:14 会自己醒来。
- 状态和定时由 `session.py` 的纯函数决定。
  - 输入：now、交易日判定结果、分时 `data.date`、分时最后一个点的时刻、行情时间戳、上一个状态、收盘数据的就绪情况。
  - 输出：（状态枚举, 是否叠加「数据延迟」, 本轮是否取数, 间隔）。
  - 后两个输入只服务于 §4.3 的过期判据，放在这里是为了让判断留在 `src/`，页面不做判断。
- 页面发现状态、间隔或取数方式变了，就 `st.rerun()` 整页，换成新间隔的 fragment。`st.rerun()` 默认 scope 是 app，控制台已在 fragment 里这样用过。
- **收盘数据的就绪时刻 `BREADTH_READY` 也算状态变化**。行情 fragment 的 60 秒时钟一旦发现时刻跨过它，就整页重跑，按钮区才会从「约 X 点后可更新」切到「更新收盘数据」。
- 集合竞价期行情字段怎么取、怎么校验，等 §10 实测后再定。

### 4.3 状态条上的时刻与过期检测

- **时刻一律用数据源自带的**：腾讯取 `sh000001` 的 `[30]`，新浪取 `[30]+[31]`；**不用渲染时刻**。原因是多标签页共享 25 秒缓存，渲染时刻和数据时刻对不上。
- **过期判据**：只在连续竞价时段（9:31–11:30、13:01–14:57）判断，满足以下任一就叠加「数据延迟」：
  - 主判据：`now −（腾讯分时最后一个点的时刻 − 1 分钟）> 3 分钟`，分时点按分钟结束时刻标注；
  - 分时拿不到时：`now − 行情时间戳 > 120 秒`。
- 「数据延迟」是**叠加标记**，不是独立状态：状态条写成「交易中 · 14:31:07 · 数据延迟」，取数与间隔照旧。它的变化**不触发**整页 rerun，否则网络一抖就每 30 秒重跑一次整页。
- 收盘后不做过期检测：实测收盘后腾讯、新浪沪市的时间戳会跟着请求时刻往前走（新浪深市停在 15:00），已经不能说明数据新旧。

### 4.4 页面上的 fragment

| fragment | 内容 | 定时 |
|---|---|---|
| 行情 | 状态条、指数、成交额、分布、温度计 | 按 §4.2 |
| 按钮区 | 收盘数据任务的按钮与进度 | 有任务在跑时 2 秒（沿用 `ui.AUTO_REFRESH_S`），状态一变就 `st.rerun()` 整页，顺带刷新宽度卡片；空闲时不挂自己的定时，由行情 fragment 的 60 秒时钟在跨过 `BREADTH_READY` 时触发整页重跑 |

宽度卡片不在任何定时 fragment 里。

**文案**：页面上不出现「今日」「今天」，一律写具体日期或时刻。两个板块日期不同时（例如盘中数据属于 9 月 23 日、收盘数据截至 9 月 22 日），各自标注，不合并成一句。

## 5. 「更新收盘数据」任务

### 5.1 登记

- `jobs.JOBS` 新增 `market_breadth`：
  - 显示名「更新收盘数据」，入口 `scripts/run_market_breadth.py`，**无参数**；
  - `parser=progress.parse_market_breadth`；
  - `result_kind="market_breadth"`（控制台不渲染它的结果）。
- 沿用现有闸门：argv 白名单、独立进程、同一时间只跑一个任务。
- 控件只放在首页按钮区，`JOB_HELP` 的说明挂在按钮区的 `?` 上。
- 控制台名单检查 `_check_roster` 加一类「在别的页」（`_ELSEWHERE`）。
- 它在跑的时候，各页控制条的「去『任务控制台』看进度与日志」（`ui.py` 的 `control_bar`）和控制台的忙碌提示，都改为指向「市场概览」。控制台上没有它的进度，也没有它的停止按钮。

### 5.2 每次运行做的事

1. 清理 `data/market/` 与 `daily/` 两处遗留的 `*.tmp`。
2. `login` 后取交易日历，请求范围 **[今天 − 500 个日历日, 今天 + 60 个日历日]**，连同实际覆盖的起止日期一起存盘。
   - **日历完整**的定义，每条都能直接写成断言：
     - 返回的日历日从「今天 − 500」起逐日连续、没有缺日，末日 ≥ 今天；
     - 「最近一个已结束的交易日」及之前的交易日（`is_trading_day == "1"`）至少有 310 个。
   - 日历不完整就报错退出，不猜窗口、不删文件。
3. 目标窗口 = 截至「最近一个已结束的交易日」的最近 **310 个交易日**。
   - 310 = MA200 要 200 天，52 周要 250 天，再加小图 60 天。
   - `BREADTH_READY`（暂定 17:30，按 §10 实测再定）之前，窗口末端是上一交易日；之后才包含当天。
4. 列出窗口内**缺的日子**（日历交易日 − `daily/` 里已有的文件名），**从新往旧**逐日调用 `query_daily_history_k_AStock`。
   - 每天拿到后先校验，通过就原子写盘：`mkstemp(suffix=".tmp")` 再 rename，沿用仓库现有写法。
   - **每存 5 天就全量重算一次指标表并原子写盘**；正常结束、出错退出时也各重算一次。
   - 这样随时停止都不丢已算好的指标，「十几分钟后就有近期的 20 日线占比」才成立。停止任务是 SIGTERM 加 10 秒后 SIGKILL，脚本不装信号处理。
5. 执行保留规则（§5.5）。只要日历完整就执行，**与本次补数成败无关**：删除是否安全只取决于日历，不取决于取数。

**所有 baostock 读取都走 `baostock_provider._fetch`**：它先判 `error_code`、再逐行读，读完再判一次错误码。
- `_check` 改为抛一个带 `code` 属性的 `RuntimeError` 子类，现有调用方不受影响。
- 任务按 `code` 区分：会话类错误（`10001001` 等，清单在实现时从 baostock 源码的错误码常量里取）→ 重新登录；其他非 0 错误 → 该日失败。
- **0 行只可能是 error_code 为 0 的真空结果**，只走下表的「当天未发布 / 过去日」分支。

**每日快照的校验**（任一不过就不存，并报错说明是哪一天）

- 所有行的 `date` 都等于请求日；
- 代码唯一；前缀只有 `sh.`/`sz.`；
- 行数 ≥ 4000，且不少于相邻已存快照中较小那份的 98%，用来挡住入库中途只拿到一部分的快照；
- 交易中的行 `preclose > 0`，且 `|pctChg − (close/preclose − 1)×100| ≤ 1e-3`；
- 入库时转换类型：`tradestatus`、`isST` 从字符串 `"1"`/`"0"` 转成整数，`close`、`preclose` 转成浮点。

**异常语义**（全部是不报错但会结论错的坑，逐条测）

| 情形 | 处理 |
|---|---|
| 当天（已过 `BREADTH_READY`）返回 0 行，**或当天快照没通过校验**（例如入库中途，行数不到 98%） | **只跳过当天**，继续往旧补完其余缺口并重算。结束语「已补到 X 日；Y 日的收盘数据还没发布，稍后再试」，算正常结束 |
| 过去的交易日返回 0 行、快照没通过校验，或**非会话类 error_code 非 0** | 重试 1 次；仍不行就在 `gaps.json` 里给这一天追加一次「失败自然日」，**继续往旧补**，最后重算，以失败结束，并在结束语里列出这些日期 |
| 某个过去交易日在 `gaps.json` 里累计有**两个不同自然日**失败 | 置 `permanent`，视为数据源的**永久缺口**：以后不再重试，也不再让任务失败。卡片按 §5.3 的缺口规则显示「—」，并注明缺的是哪天 |
| 会话类 error_code（`10001001` 等） | 重新 `login`，重试该日，最多 2 次。仍失败就停止补数（没有会话无法继续），重算后以失败结束；这种失败**不计入** `gaps.json`，它是本机会话的问题，不是数据源缺数 |
| 被用户停止 | 已存的日子与最近一次重算的指标表都保留；下次从缺口继续 |

**日志与进度**（面板重启后，runner 只凭日志判断任务成败，所以格式写死）

- 开头一行：`待补 N 天`。N 是本次缺的天数（不含永久缺口），日常增量通常是 1。
- 每处理一天打一行，无论成败：
  - 存下：`[i/N] YYYY-MM-DD 5220 行 用时 18.4s`；
  - 没存：`[i/N] YYYY-MM-DD 跳过：<原因>`。
  - parser 按这两种行计数，用最近 10 个存下的日子的平均用时估算剩余时间。
- **只有**整轮成功，或只缺「当天未发布」时，才打收尾标记 `全部完成: …`（已在 `DONE_MARKERS` 里），退出码 0。
- 有过去的日子失败时，不打收尾标记，退出码非 0。
- **这个脚本的日志全文任何位置都不得出现子串「已保存:」**——不只是行首。`process` 判成败用的是子串匹配（`marker in log`），所以「指标表已保存: …」这种话也会让失败的一轮在面板重启后被记成成功。测试按子串断言。
- 给 `parse_market_breadth` 配 `tests/fixtures/*.log` 回归夹具，和现有三个 parser 同法。夹具要包含一份失败路径的日志，经 `_reap_zombie` 判定必须是失败。

### 5.3 指标定义

- **范围**：当日交易中（`tradestatus=1`）、非 ST（`isST=0`），且至少有 N 根历史。没有单独的新股过滤：有 N 根（N ≥ 20）历史的股票必然上市满 N 个交易日。
- **复权收盘**：每只股票**所有行都参与连乘** `close/preclose`。
  - 停牌行 `preclose` 无效时比值记为 1；停牌行出现 `close ≠ preclose` 时打日志报警。
  - 停牌行不计入均线的根数。
  - 这样写，除权日落在停牌期时也不会把除权缺口当成真跌。
- **缺口**有两种：整天缺失，或某只股票在首次和最后一次出现之间缺了某个交易日的行。回看期跨过缺口的指标一律记为缺值：不进分子也不进分母，页面显示「—」，不硬算。判定按这 N 根实际覆盖的日期区间。
- **站上 N 日线**：当天复权收盘 > 该股最近 N 根（含当天）复权收盘的均值。分母是范围内、至少有 N 根历史的股票。表里同时存分子和分母。
- **52 周新高/新低**：当天复权收盘 ≥ 最近 250 根（含当天）的最大值为新高，≤ 最小值为新低。「根」与均线同一口径，不计停牌行。分母规则同上。
- 所有比较都用相对容差 1e-9，防止连乘的浮点误差让追平的情况时有时无。
- 指标表每次都**全量重算**：修正算法后，历史跟着一起更新，不会出现新旧算法混在一张图上。

### 5.4 首页按钮区的状态

按顺序判定，命中第一条即停。

| 状态 | 显示 |
|---|---|
| 任务状态文件损坏 | 报错说明，不给按钮（沿用 `control_bar` 的做法） |
| 正在运行 | 进度 + 「停止」 |
| 有别的任务在跑 | 「有任务在运行，稍后再更新」 |
| 上次失败 | 最后一条错误，可展开完整日志。按钮：`daily/` 里还没有合格快照就是「开始准备」，否则是「更新收盘数据」。这一条排在「从没准备过」之前：第一次准备还没存下任何一天就失败了，也要让人看到错误，因为控制台不渲染这个任务 |
| `daily/` 里没有任何合格快照 | 一句说明（「趋势宽度需要约一年的收盘数据，第一次准备大约 {breadth_first_run}，可随时停止、下次接着补」）+「开始准备」 |
| 缺日子且可补（不含已登记的永久缺口） | 「更新收盘数据」 |
| 今天是交易日、`BREADTH_READY` 前、已补到上一交易日 | 小字「9 月 24 日的收盘数据约 {breadth_ready} 后可更新」，无按钮 |

某项指标历史不足时，卡片上写「还差约 N 天的收盘数据，点『更新收盘数据』继续」。只有遇到补不上的永久缺口，才写「还需约 N 个交易日」。

时刻和耗时一律走 `FACTS`，新增两项：`breadth_ready` 引用 `quant.market.BREADTH_READY`；`breadth_first_run` 是首次准备耗时。**不复用 `data_ready`**（见 §2「分层」）。FACTS 的每一项都必须逐字出现在 README 里。

### 5.5 存储与保留

- 目录 `data/market/`：**加进 .gitignore**；可以重新下载，不进「换电脑要拷什么」清单。
  - `daily/YYYY-MM-DD.parquet`：每日快照，只存 `code, close, preclose, tradestatus, isST`，类型已转换；
  - `breadth.parquet`：指标表；
  - `calendar.parquet`：交易日历，附带覆盖的起止日期；
  - `gaps.json`：补不上的日子。结构 `{"2026-08-14": {"failed_on": ["2026-09-24", "2026-09-25"], "permanent": true}, …}`。
    - `failed_on` 是**失败时的自然日**（脚本启动时的 `date.today()`）去重后的列表，同一天里重试多次只记一次；
    - 出现两个不同自然日就置 `permanent: true`；
    - **只有 `permanent: true` 的条目**才算永久缺口：§5.2 的「待补 N 天」和 §5.4 的「缺日子且可补」都只排除它们，`permanent: false` 的日子照常重试。
- 首页只读这四样：`breadth.parquet`、`calendar.parquet`、`gaps.json` 和 `daily/` 的**文件名**，任何一样读失败就逐块降级。日历只在它覆盖的范围内当作权威，超出范围当「未知」，**绝不当作休市**。
- **滚动窗口**：每次运行只要日历完整，就删掉 `daily/` 里早于窗口首日的快照（与本次补数成败无关）。稳定状态下约 310 份，预计 20~90 MB，实测后写进 README。删除有三条限制：
  - 只删文件名严格匹配 `^\d{4}-\d{2}-\d{2}\.parquet$` 的文件，别的一概不碰；
  - 窗口按**交易日**算；
  - 日历不完整时**不删**。

## 7. 代码结构

```
src/quant/market/
  sources.py    # 腾讯/新浪/东财：拼 URL、取数（注入 http_get，默认 requests，带超时）、解码、按源解析与校验 → dataclass
  live.py       # 一轮两段式并发取数 + 主备取舍 + 最近成功值（可 reset 的对象）
  session.py    # 交易日判定链 + 状态表（纯函数：now、日历、源日期、上一状态 → 状态枚举/本轮是否取数/间隔）
  breadth.py    # 快照 → 复权链 → 指标表（纯函数）
  store.py      # data/market/ 读写、原子写、保留规则、日历完整性、永久缺口
  __init__.py   # BREADTH_READY：收盘数据就绪时刻的唯一出处，guide.FACTS 与任务脚本都引用它
src/quant/report/minicharts.py  # 分时、分布、宽度小图 → SVG 字符串 → data URI（色值来自 palette）
scripts/run_market_breadth.py   # 任务入口（baostock 会话、补缺、日志格式）
app/pages_home.py               # 只排版；文案常量在 guide.py（HOME_ 前缀）
```

判断与格式化一律放在 `src/` 的纯函数里，页面只做排版，沿用 steps.py / fmt.py 的分层。`src/` 与 `scripts/` **不 import `app/`**：`session.py` 只返回状态枚举，文案映射在 `guide.HOME_`。

## 8. 测试

- **全局隔离**（`conftest.py`，autouse；每个 AppTest 都会先渲染落地页，所以这是前提）
  - `http_get` 换成离线替身，返回录制数据；
  - **冻结首页用的时钟**，固定在录制数据那天的收盘后，与夹具的 `data.date` 一致；
  - 每个测试前后 `st.cache_data.clear()`，并 reset 最近成功值；
  - 在 requests 发送层装守卫：非 network 测试里一旦真实联网就直接失败。
- **解析与校验**
  - 样本用实现时**现场录制**的真实返回，存 `tests/fixtures/market/` 并注明录制时刻；6 只指数的分时都要录。
  - 变异测试，每种都必须被拦下：字段下标错一位、涨跌额对不上、批量请求里整段缺失、单个请求返回 `v_pv_none_match`、新浪日期不对、分布缺档、池子家数 ≠ 明细数、空池配上 +11 档 > 0、过期比较方向写反。
- **时段判定**（表驱动）
  - 单点：每个时段边界；日历覆盖/不覆盖今天；源日期 = 今天、早于今天、请求失败。
  - 状态转移：11:29:50 → 11:30:20 → 12:59:50 → 13:00:20；08:59 → 09:14:30；前一天 20:00 → 次日 09:15；`BREADTH_READY` 前后（按钮区要跟着变）。
  - 9:14–9:44 全部失败、9:46 成功且日期是今天 → 必须是「交易中」，不是「休市」。
  - 误判能自愈：9:46 判了休市、10:05 那轮拿到今天的日期 → 回到「交易中」。
  - 没有日历时：周六一律「休市」；节假日（工作日、源日期是昨天、分时全失败）→「状态未知」，**不能**是「交易中」。

  - 日历说是交易日、但源日期过了截止时刻仍是昨天 → 「交易中」加「数据延迟」标记，各板块标数据自己的日期。
  - 「数据延迟」出现或消失时**不**触发整页 rerun。

## 9. 不做（及原因）

- **恐慌指数**：用户 2026-09-23 决定先不要。调研结论留档：
  - 官方没有：中国波指 iVIX 于 2018-02-22 暂停，至今未恢复；中证、国证、上交所、中金所的完整指数清单里都没有 A 股波动率指数。
  - QVIX（期权论坛）数据质量不可用：有整行复制、周末日期、错位、开高低收矛盾，站方还会事后补插复制行。
  - 用新浪期权全链自己按 VIX 公式计算可行：1 次请求、约 120 行代码，今天收盘算出 300ETF 15.56，比 QVIX 低约 2%，差距来源不明。
  - 没有现成的指数历史：可以用新浪期权合约日线按收盘价回填，但每个合约要 1 次请求，回填一年要几百到上千次。日后要做，从这里起步。
- 北向资金净流入：2024-08 起交易所不再披露。
- 主力资金流、行业/概念板块实时排行：东财要 cookie，而且资金流口径是它自定义的。
- 两融余额、市场估值分位：用户这次没选；全 A 估值分位的来源在 robots.txt 里明确禁止抓取。
- 北证50、中证500 卡片；自定义指数列表；宽度的长历史（超过 60 日的图）；盘中「较上一交易日 %」。
- akshare：不引入。它会新增 15 个包、约 220 MB；约 95% 的请求没有超时；接口坏了只在最新版修。它只作为「接口地图」参考。
