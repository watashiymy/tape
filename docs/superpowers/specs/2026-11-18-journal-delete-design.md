# 「记账」页历史记录的删除：每行一个按钮 + 确认框（2026-11-18，当天第三轮）

分支：`feat/journal-delete`（从 main a0f220e 拉出，工作区在 `.claude/worktrees/journal-delete`）。
事后补的设计记录。本文与测试里的例子一律用虚构的票和数（仓库是公开的，用户的交易记录不进仓库）。

## 0. 起因

用户对着「记账」页的「历史记录」说（原话）：

> "记账"页面的"历史记录"，"删除"的交互有点太奇怪了：
> 1. 为什么"删除"的选择框要放在第一列的位置
> 2. "先勾选要删除的记录、再点击保存"——很奇怪的交互
>
> 你看看要怎么改，才有一个比较合理的交互逻辑

## 1. 原先为什么是那样

- **删除是一列勾**：历史记录是一整块可编辑的表格（`st.data_editor`），当初的思路是"表里的改动先攒着，
  点一次「保存修改」一起写入"——改一格是改动，删一行也被当成一种改动，所以做成了表里的一列勾选框。
- **勾完还要点保存**：故意留的两步。这份记录删了找不回来，怕手滑。
- **在第一列**：是 2026-11-16 那一轮我挪的，用户当时没逐项点过头。它原先在最右——这张表十六列，
  要把表横着拖到头才看得见；这种表格只能把列钉在左边，就钉到了第一列。

合起来成了：一列叫「删除」的勾，勾了什么都不发生，还得去点一个叫「保存」的按钮。两步本身没错，
错在两步都不叫删除。

## 2. 摆给用户看的几种做法

没有写方案文档，在 `/tmp` 的副本里把几种做法都做成能点的，历史记录上方放一条只在预览里有的切换：

| 做法 | 怎么删 | 代价 |
|---|---|---|
| **行内删除按钮**（用户选的） | 每行最前面一个垃圾桶 → 确认框写明是哪一条 → 确认即删 | 一次只能删一条；按钮只能在行首 |
| 勾选后删除 | 最左是不带名字的勾（选中这一行）→ 表格下面「删除选中的 N 条」→ 同样的确认框 | 多一步；好处是一次能删多条 |
| 按钮放行尾 | 同第一种，按钮在最右（后台表格的常见位置） | 要把表横着拖到头才看得见 |
| 原先的做法 | 勾「删除」再点「保存修改」 | —— |

我建议第一种（这本账是偶尔删一条，最短的路最合适），用户选的也是它。
这一版 Streamlit（1.61.1）的可编辑表格支持按钮列（`ButtonColumn`）与弹出式确认框（`st.dialog`），
所以不必再借「保存修改」绕一道。没有考虑表格自带的删行（`num_rows="delete"`）：行当场从表里消失、
却还得点保存才算数，仍是两步，而且垃圾桶藏在悬停才出的工具栏里。

## 3. 现在的做法

```
历史记录（共 7 条） ?
▸ 筛选
┌────┬────────────┬────────┬──────────┬──────┬─────────┬────────┬───
│    │ 日期       │ 代码   │ 名称     │ 类型 │ 股数    │ 成交价 │ …      ← 前四列钉在左边
│ 🗑 │ 2026-08-03 │ 000333 │ 美的集团 │ 买入 │ 1000.00 │ 71.500 │ …
│ 🗑 │ 2026-08-24 │ 000333 │ 美的集团 │ 卖出 │ 1000.00 │ 75.000 │ …
└────┴────────────┴────────┴──────────┴──────┴─────────┴────────┴───
          ☐ 确认用上一版覆盖当前记录 [恢复上一版]  [导出 CSV] [导出 Excel] [保存修改]

点某一行的 🗑 →
┌ 删除记录 ──────────────────────────────────────────── × ┐
│ 要删除这一条记录吗？                                      │
│  • 2026-08-24 卖出 美的集团（000333） 1,000 股 × 75.00    │
│ 表里另有 1 行改动还没保存，会一起保存。                   │  ← 只在表里别的行有没保存的改动时
│ 「恢复上一版」现在还能换回下面这 1 条。这次删除之后就     │  ← 只在上一版里还有"现在已经没有"的记录时
│ 换不回来了——还想要的话，先点「取消」，再去恢复。          │     （连着删第二条就是这样）
│  • 2026-08-03 买入 美的集团（000333） 1,000 股 × 71.50    │
│ 这一条删错了，可以用表格下面的「恢复上一版」换回。        │
│ ┌ 没有删除，也没有保存（表里下面这些行改坏了……）─────┐  │  ← 只在删不成的时候
│ └────────────────────────────────────────────────────┘  │
│                                        [取消] [🗑 删除]   │
└───────────────────────────────────────────────────────────┘
```

- **点 → 问 → 删**。点某一行的删除按钮，弹确认框；点「删除」才删，删完右上角提示
  「已删除 1 条记录。删错了可以点「恢复上一版」换回。」。取消、从右上角关掉、按 Esc，文件一个字节都不动。
- **「保存修改」只管改动**。它下面那句提醒也只数改了几行。
- **防误删靠两样**：确认框（写明是哪一条——哪天、买还是卖、哪只票、多少股、什么价，
  `journal_ui.describe_trade`），和删之前照旧留下的上一版。

代码在哪：按钮列与它的键、点击回调、等着确认的请求、把一条记录写成一行字、确认框要说的三样东西、
按记录号删除都在 `app/journal_ui.py`（`editor_columns` / `delete_click_key` / `on_delete_click` /
`clicked_id` / `pending_delete` / `forget_delete` / `describe_trade` / `delete_plan` / `only_in_backup` /
`delete_trades`）；确认框在 `app/pages_journal_entry.py`（`_confirm_delete` / `_delete_dialog`）；
离开本页时撤掉请求的那一句在 `app/dashboard.py`；文案在 `app/guide.py`（`JOURNAL_DELETE_*`）。
落盘那一层（`quant.journal.store`）没有改。

## 4. 几个要说清的决定

**按记录号，而且是"画那张表的那一轮"的记录号。** 按钮交回来的只是"第几行"。把它换成记录号用的是
随列配置一起注册的那一轮各行的记录号（`on_click` 的 `args`），不是等点击那一轮重新读了文件再按行号查：
表里显示的是筛选后的行；另一个标签页若刚删过一条，重新读到的表里每一行都上移一格，按新表的行号去认，
认到的是下面那一条。使用者点表头排序之后，按钮交回的仍是原始数据的行号（读前端源码确认过，
真实浏览器里也验过：排序后点第一行的垃圾桶，确认框里是排在第一行的那一条）。
点的那一条若已经不在了，不开确认框，只说一句。

**按钮那一列自己的键，也跟着这一轮的记录号走**（独立审查后加的）。按钮列是个独立的控件，身份只看它的键。
初稿用固定的键，于是旧表与新表上的按钮是同一个控件：后台已经把新的一批行画出去、浏览器还没换上的
那几十毫秒里，旧表上的一下点击会被拿去按新表的记录号认——审查者用真实的键盘鼠标事件复现了：
筛选框里按回车之后 28 毫秒点第二行的垃圾桶，确认框里写的是筛选后同一位置的另一条。
现在键里带着这一轮记录号（连同先后）的指纹（`delete_click_key`），表里换了内容，旧表上的按钮就不再是
同一个控件：它的点击要么按旧表自己的记录号认，要么作废。与那张表刻意不带 key 是同一个道理——身份取自内容。

**确认框从点击起一直在，直到回答或关掉**（独立审查后改的；初稿相反）。回调把记录号登记在 session_state 里，
页面每一轮都照它在页尾把确认框（再）开出来。初稿是"只在点击那一轮开、页面一开头就把请求取走"，
理由是怕它留到以后不请自来——结果在很平常的状态下第一下删不动：确认框一弹出就抢走焦点，上面表单里
敲了字还没回车的输入框当场失焦提交，引出一次整页重跑，框就没了（真机：出现 87 毫秒后消失）；
表格里刚改完没回车的那一格，一百多毫秒后也会引出一次。现在这两种重跑关不掉它，后一种还会让框里
补上「会一起保存」。"不请自来"改由逐个堵住来保证：答过了、关掉了（`on_dismiss`）、点的那一条不在了、
这一页读不出文件、去了别的页（`dashboard.py`），都撤掉那次请求。
确认框仍排在整页画完之后才开：这个项目栽过"页面中途重跑，还没画出来的控件丢一轮状态"。

**删不成的时候，框不关，原因写在框里**（独立审查后加的）。别的提示都在页面最上面，人正盯着下面的表格，
那里的一句红字等于没说——审查者量过，那句话在视口上沿之外，看到的只是"点了删除、框关了、什么都没发生"。
现在别的行改坏了、那一条刚被别处删了、写盘失败，原因都写在框里两个按钮的上面，框留着。

**表里别的行上有没保存的改动时：一起保存。** 删完表里的内容变了，表格会换成一张新的（它不带 key，
身份取自内容），那些改动留不住。三条路里选了"一起写进去"：悄悄丢掉最糟；先拦住、让人保存完再来删，
多绕一步；一起写是一次写入、一份上一版，不想要可以整个换回——前提是确认框里事先说明。
那些改动里有校验不过的行，就整个不写（不删、不存），理由同「保存修改」。正要删的那一条身上的改动不算数。
框里说"另有几行"数的、与确认之后写进去的，是同一份（`delete_plan` 交回的那张表）。

**连着删：说在前面，不替人保住。** 上一版只留一版，删第二条时它会从"两条都在"换成"只少第一条"，
第一条从此换不回来。考虑过让连着的几次删除共用最早那份上一版（恢复时一起回来），也跟用户提过，
没有做：那样恢复会把**故意**删掉的前几条也带回来，而恢复之后页面上只有一句"已恢复上一版"——账上多出
一条错的记录，比少一条更难发现。现在的做法是在删第二条的确认框里当场说明，并列出是哪几条
（`only_in_backup`：上一版里有、整本日志里没有的记录），还想要就先取消、去恢复。最后那句"删错了可以换回"
点名说的是「这一条」——它紧跟在"换不回来了"后面，不点名读着像自相矛盾（真机上看到的）。

**按钮的样子与位置。** 只有一个垃圾桶图标、不描边、表头不写字、宽 48 像素，与日期 / 代码 / 名称一起钉在左边
——表横着拖去看备注时还删得到。在行首而不是行尾是表格的限制（见 §2）。

**没变的纪律**：编辑器仍然不带 key；落盘仍在锁里重新读整本日志再改；什么都没改时点保存仍不写盘。

## 5. 测试

全量：2814 passed，1 skipped，6 deselected（改之前 2759 passed）。

`tests/test_dashboard_journal.py` 里原先"勾选 + 保存"的那一批全部改写，新增的主要是：

- 按钮列的配置、键与接线；行号换记录号（含没有点击、正好越界的那一个行号）；
- 确认框写了什么、两个按钮的位置；取消 / 确认 / 关掉各自的结果；
- 确认框的寿命：别处引起的整页重跑不关它、晚到的改动让它补上「会一起保存」；答过 / 关掉之后不再回来；
  文件读不出来、离开本页、点的那一条在框开着时被别处删掉——请求都撤掉；
- 筛选后的表里删的是屏幕上那一行；另一个标签页改过文件之后点的仍是屏幕上那一条；
  后台已经换了一批行之后才到的旧点击作废；框开着时那一条被筛出了表外，问的仍然是它；
- 别的行有没保存的改动时的说明与一次写入；那些改动是坏的——框不关、原因在框里；点了又取消之后改动还在；
- 连删第二条时的说明（顺序、是哪一条），没有这回事时不说；只是被筛掉的记录不会被说成"换不回来"；删到一条不剩；
- 落盘那一层脱离页面的几条（按记录号删、记录不在了、写盘失败、顺带保存、确认框要说的三样东西）。

`tests/test_concurrent_writes.py` 补了两条真线程的：八个标签页同时各删一条，八条都得删掉；
以及一条对照——不加锁地做同一件事，删掉的记录必然有回来的（证明前一条测得到东西）。

AppTest 只会整页重跑，而真实浏览器里确认框的按钮只重跑框里的内容。确认框从点击起一直挂着之后，
测试可以照人那样分两轮走（`_click_delete` 一轮、`_answer` 一轮），框里的按钮在整页重跑时照样接得到。
初稿（框只开一轮）时只能把两下并进同一轮，审查者指出那正是"框闪一下就没了"漏过去的地方。

### 独立审查（2026-11-18，一轮）

实现做完后交给一个没有上下文的审查者，只给它代码差异与"这次应该做成什么"。它自己在真实浏览器里起了副本，

丢数据或丢撤销手段的落盘路径，但——

| 审查意见 | 核实 | 处理 |
|---|---|---|
| **确认框会被它自己引出来的整页重跑关掉**：表单里敲了字没回车、筛选词没回车、表格里刚改完一格没回车，去点垃圾桶，框闪一下就没了 | 我自己复现了第一种：框出现 87 毫秒后消失 | 确认框改成从点击起一直在（见 §4）；修后三种都复验过 |

| 删除被拒时原因写在页面最上面，人在表格那儿看不到 | 成立（别的提示确实都在页顶） | 框不关，原因写在框里；真机复验过 |
| 说法与行为对不上：README 说删除之后没保存的改动"一律作废"（其实一起保存）；一条测试的说明说保存也只写改过的行 | 成立 | 文字改对 |

### 真机验收（隔离副本、虚构账本，1440×900 与 1024×768 各一遍）

副本在 `/tmp`，账本是另造的一份虚构记录（美的集团 / 贵州茅台 / 招商银行，八条）；给用户看的那份副本里是
他账本的拷贝，验收没有碰它；主目录的 `journal/` 自始至终没动（校验和与修改时间前后一致）。

两种宽度下都走过的状态：有数据时的表格与按钮行；点垃圾桶 → 取消；确认删除；连着删第二条（框里列出
换不回来的那一条，账本与上一版逐项核对过）；恢复上一版；筛选生效时删除（筛选条件与展开着的折叠区都还在）；
表里有一处没保存的改动时删除（取消后改动还在；确认后一次写入，上一版是写之前的样子）；点表头排序后删除；
删到一条不剩再恢复；空账本。只在 1440 下看过的：从右上角关掉、按 Esc、框刚开时按回车（不会确认——
焦点在框本身，不在按钮上）、双击「删除」（只删一次）、表横着拖到头时垃圾桶仍在左边。

审查之后（修完）在 1440 下复验的：表单里敲了字不回车去点垃圾桶（框一直在）；筛选词不回车去点（框一直在，
问的仍是点的那一条，尽管它已经被筛出表外）；表格里一格正开着编辑框去点（框先开，约 100 毫秒后补上
「会一起保存」）；别的行改坏了时点删除（框不关，原因在框里，页面最上面没有）；从右上角关掉之后再触发几次
重跑（不再回来）；框开着时去别的页再回来（不再回来）。

**没法照人那样做、或者没做的**：

- 「确认用上一版覆盖当前记录」那个勾是用脚本触发的点击勾上的（自动化工具点不动 Streamlit 的勾选框），
  之后的按钮是照常点的；框开着时去别的页，也是用脚本点的侧边栏（确认框挡着，鼠标点不到）。
- 回车后几十毫秒内点垃圾桶的那个时序（上表第二行），修完之后我没有在真实浏览器里重新造出来验证，
  靠的是那条测试与审查者在原型上的测量。
- 往表格的文字格子里打字只成功了一次（就是上面"正开着编辑框"那一条），别的"没保存的改动"用的是下拉列。

## 7. 没做的 / 留给以后

- **「恢复上一版」仍是"先勾确认框、再点按钮"**——与用户嫌别扭的是同一种做法。预览里做过一版确认框
  （写明恢复后哪几条会回来、哪几条会消失）给他看，问了要不要一并改，他还没表态，正式版没有动。
- **写盘失败时，上一版照样被换掉**（旧的，审查顺带报的，落盘那一层的事）：`store.save_trades` 是先备份、
  再写正式文件，正式文件没写成时上一版已经换成了当前这一版。对所有写入都一样，不只是删除。
- 顺带保存写的是开框那一刻的**整行**：框开着期间另一个标签页改了同一条记录的别的列，会被旧值盖回去
  （「保存修改」一直如此，而且是整张表）。场景很窄，没有动。
- 上一版读不出来时确认框不提这件事；手工改坏的文件里记录号重复时，点删除得到的是"已经不在了"
  （安全，话不准）；删完表格是一张新的，使用者点的排序会复位（不带 key 的既定代价）。
- 校验信息里还有一句夹着内部键（「无法解释的记录类型 'nan'，只支持 buy/sell/adjust/dividend」），
  旧的，这次它会出现在确认框里。（同一天稍后单独改了，见 `2026-11-18-kind-message-design.md`。）
- 顺带看到的旧问题：表格右上角的悬浮工具栏（四个小图标）在鼠标停在表上、或者表里选中着一格的时候会显出来
  并上移约 42 像素，盖住表格上方靠右的控件。有筛选生效时盖的是「清除筛选」按钮下面约三分之二（1440 宽下
  量的：先点一下表里的格子，再点按钮的下半截——筛选还在）；筛选折叠区展开且没有筛选条件时盖的是
  「理由关键词」输入框的右下角（1024 宽下约七成）。这一段版式这次没有动过，主分支上一样。
- 「记账」页页顶那个折叠说明（这一页记什么、四种记录类型的含义）仍在，用户没提，没有动。
